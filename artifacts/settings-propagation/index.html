When Settings Reach a Session

Use claude respawn --all for background sessions that need a full restart. Interactive and editor sessions restart when you close and reopen them. You usually do not need to restart sessions after adding or changing a live-reloaded setting.

Save the file → applies

Adding or changing an env value reaches a running session the moment you save.

Delete the line → waits

Removing an env value does not unset it in a running session. It takes effect at the next launch.

Restart only sessions that need it

Session typeRestart methodWhat it preserves
Background sessionclaude respawn <id> or claude respawn --allRestarts one or all background sessions
Interactive terminalExit and run claude again; claude --continue resumes the conversationConversation state when using --continue
Desktop app, VS Code, JetBrainsClose and reopen the chat tabStarts a new session

claude respawn --help gives the usage claude respawn <id>|--all and describes it as "Restart a background session (or all of them) so it picks up the current Claude binary." Re-reading startup-only settings is a consequence of restarting the process, not an advertised feature.

Removing environment values requires relaunch

The Claude Code environment-variable documentation states:

A running session applies new and changed values to its environment when you save the file, but a feature that reads its variables once at startup, such as OpenTelemetry monitoring, keeps its startup values until you relaunch.

Removing a variable from the file doesn't unset it in a running session; the removal takes effect the next time you launch claude.

The important asymmetry is: adding or changing an env value reaches a running session when the file is saved, but removing an env value does not unset it there. Restart only when the removal must take effect, or when the consuming feature reads the value only at startup.

Most settings reload while running

Claude Code watches settings files and reloads several categories during a session, as documented under When edits take effect:

  • live permissions rules in the allow, ask and deny lists.
  • live hooks.
  • live Credential helpers such as apiKeyHelper.
  • A ConfigChange hook fires for each detected settings change.

Some settings remain startup-only

The documented startup-only list is partial:

  • restart model — use /model to switch during a session.
  • restart effortLevel and modelSettings — use /effort during a session.
  • restart Administrative keys such as requiredMinimumVersion.

Precedence can override visible edits

Settings sources have this precedence, highest first:

  1. Managed settings from organisation policy or MDM.
  2. Command-line settings supplied with --settings.
  3. .claude/settings.local.json
  4. .claude/settings.json
  5. ~/.claude/settings.json

Environment variables are resolved per key rather than by file level. For example, an ANTHROPIC_MODEL exported by the shell overrides a model key from any settings file.

Stale process environments can mislead

CLAUDE_CODE_ATTRIBUTION_HEADER=0 was removed from ~/.claude/settings.json because it silently broke auto mode behind a local gateway. Hours later, 16 of 33 running processes matching claude still carried it:

Processes still carrying itCountStarted
Orphaned socat UNIX-LISTEN:/tmp/claude/claude-http-*.sock forwarders1418 Aug – 2 Sep
python3 -m http.server118 Aug
claude agents TUI113 Aug

None of these processes make classifier requests. The session-spawning daemon, claude daemon run, did not carry the variable, so every background session it starts inherits the corrected environment.

"Still in some process's environment" is not the same as "still affecting your sessions." Check what the process actually is before restarting anything.

Other settings traps delay changes

  • Workspace trust gates permissions.allow, permissions.additionalDirectories, extraKnownMarketplaces and most env values until the folder is trusted.
  • A broken settings file raises a Settings Error at interactive session startup; a -p run prints the error and exits.
  • If ~/.claude.json is corrupted, recovery uses a recent .claude.json.backup.<timestamp> file from ~/.claude/backups/; that directory exists but is currently empty on this machine, so it is where backups appear, not where one is waiting.
  • Keys scoped User, local or Managed are never read from a shared .claude/settings.json, so a committed key might not reach a teammate.
  • Managed settings delivered by MDM or the console reach running sessions on a refresh schedule; the interval depends on the delivery mechanism.

Checking what is actually live

  • /status shows which settings files were loaded, but not which file supplied a given key.
  • /config views and changes a limited set of personal settings.
  • claude doctor, the CLI command, is read-only install and settings diagnostics.
  • /doctor, inside a session, is an interactive checkup that can apply fixes.
