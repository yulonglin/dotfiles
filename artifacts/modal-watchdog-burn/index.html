Post-mortem · 16 September 2026

The watchdog that wouldn't stop

A health check ran every 180 seconds against a 300-second idle timeout. That one gap held an H100 awake for 31 days.

What it was supposed to do, and what it did

The script was solving a real problem. It was written on 14 August because the vLLM endpoint wedged every 20–40 minutes under load — /health would accept a connection and return zero bytes, hanging any client. A long evaluation run would die partway through, and someone had to redeploy by hand each time. What was wrong was the shape of the solution: an external control loop where the platform had a declarative setting, which is the subject of a later section.

So the watchdog polled /health, and after three consecutive failures ran modal deploy to revive it. During the run, it worked exactly as intended.

Intended as designed

Poll the endpoint during an eval run. Redeploy it when it wedges. End when the run ends. Lifetime: a few hours, bounded by the work it was protecting.

Actual 31 days

Polled every 180s forever. Because 180s < the 300s scaledown_window, the container never idled out — the health check became the load. Nothing ever ended it.

Real work is bursty; an idle GPU is flat

This is the whole diagnosis in one picture. Every burst on the left is someone running evaluations — different splits, different rollout counts, interruptions, nights off. The plateau on the right is a machine nobody was using, billing the same amount every single day including weekends.

The obvious alarm is the wrong alarm

The intuitive guard is a spend threshold — tell me when a day costs more than $50. Simulated against this same 61-day series, it fires earliest and is the one to reject.

RuleFirst firesSavedFalse positives
Any day over $5013 Aug$3,056 6 — all real work
3 days running over $5017 Aug$2,7410
3 flat days, under 5% variance17 Aug$2,7410
Rolling 7-day over $50018 Aug$2,5801

Six of the threshold's firings land on legitimate eval days, and a guard that cries wolf gets muted — after which it catches nothing at all. So the rule that shipped keys on flatness, not magnitude: three consecutive days within 5% of each other, above a floor.

One honest caveat, because it changes how much the table is worth: the two zero-false-positive rules tie, and this data cannot separate them. The sample contains no legitimate run lasting three or more days above $50/day — which is precisely the case that would break the "3 days running" rule. Flatness was chosen on mechanism rather than on these numbers, and every rule here was picked after seeing the incident it is scored against.

A flat series is also not proof of waste. A long training run on a fixed allocation is flat too. So the guard asks whether the spend is still intended; it never stops anything.

The platform already had a knob for this

The sharper lesson is not that the watchdog lacked a deadline. It is that a poller keeping something alive is a configuration setting someone wrote in bash. Checked against the installed Modal 1.4.3 source, three declared parameters cover what it was doing:

ParameterWhat it declaresWhat the watchdog did instead
min_containers Keep N containers warm even when idle Achieved exactly this, as an undeclared side effect of a health check
timeout Max execution time per input (default 300s; this app set 12h) A wedged request pinned its container for up to 12 hours

min_containers=1 is the whole watchdog, in one line, in the app definition. The difference is not behaviour — it is that a declared parameter is auditable and a tmux pane is not. Nobody could see the keep-alive because it was never written down as one.

An earlier version of this page listed a third parameter, max_inputs, as a way to recycle a container after N requests. That was wrong and has been removed. Modal 1.4.3 accepts only max_inputs=1 — now spelled single_use_containers — and refuses it for web servers outright. There is no N-input recycle, so nothing declarative replaces "redeploy it when it wedges."

Three things the platform genuinely does not offer, which is why the watchdog was not simply reinventing a feature: there is no liveness probe for a deployed function — modal.Probe exists but only for Sandboxes, and @app.function takes no probe parameter; there is no way to declare an expected duration, only hard kills; and there is no container recycling short of one-request-per-container.

What did resolve is the question of what timeout bounds. For a @modal.web_server it caps each forwarded request, not the container's lifetime: the server boots once and an ASGI proxy sits in front of it, so lowering the value cannot force cold starts. That makes it the one safe lever, and on this app it was set to twelve hours.

Three guards, at three distances from the mistake

Spend monitoring is the last line, not the fix. It catches the symptom days later, whatever the cause. Two cheaper guards sit closer to the moment the mistake is made.

Before

A poll faster than the idle window is a keep-alive

A hook fires when a command looks like an unbounded network poller and carries no deadline, pointing at timeout — which already exists, so nothing new was shipped to do the job. It also asks the question that actually mattered: is the poll interval shorter than the scaledown window?

During

Removing a worktree does not kill what runs inside it

cwrm now refuses to remove a working directory with live processes in it, and cwclean keeps it. --force deliberately does not override this: that flag is about discarding build artifacts, and orphaning a running process is the more expensive mistake.

After

Flat daily spend, surfaced where someone reads it

A daily check across every cloud account flags sustained flat billing and raises it at the start of the next session. This is the backstop. It would have caught this one on 17 August — two days in, about $2,700 unspent.

The guard needed four reviewers to become safe

The hook that nudges toward a deadline was reviewed by four model families, each able to read the repository and run the hook rather than only read a diff. Every one of them found a distinct defect that would have killed it, and three of the four blocked it outright.

  • The advice never reached the agent. It was emitted only as a user-visible message, not into the model's context — so the nudge would have been seen by a human and ignored by the thing running the command.
  • It fired on the word, not the act. Matching watchdog anywhere meant mv watchdog.sh archive/, docker logs watchdog and mkdir keepalive all triggered it.
  • pip install watchdog. That is a real Python package with roughly 200M downloads, present in most of these repositories. On its own this would have trained the ignore reflex inside a week.
  • until is the opposite of a keep-alive. while curl …; do sleep; done runs while the endpoint is up — that is the keep-alive. until curl …; do sleep; done stops when it comes up: ordinary wait-for-ready. The hook fired on it, and the test suite asserted it should.

Only reviewers with tools found these. The false positives were confirmed by running commands through the live hook, not inferred from reading it — and the eight-model text-only panel, given the same code as pasted context, returned nothing at all.

The hook now carries 84 test cases. Most of them assert silence, because on something that runs before every shell command, the false positives are what kill it.

What actually goes wrong

Every layer here worked, and the money still burned. The endpoint watchdog did its job. The billing data was correct and available the whole time. The roster check that monitors the review panel had even detected a separate dead component a day earlier — and wrote it to a file under ~/.local/state/ that nothing reads.

That is the actual pattern, and it repeated twice in one investigation: a monitor that reports into a file nobody opens is not a monitor. The fix in both cases was not better detection. It was putting the finding in front of someone at the moment they could act on it.

The second pattern is narrower and worth naming: a process written for one run needs an end condition, not just a start condition. A deadline would have capped this at twelve hours. The mechanism — timeout — has been in coreutils for decades. Nobody reached for it, because nothing asked.
