Why Auto Mode Broke Behind the Gateway

Auto-mode tool calls were denied in bursts on 13 to 18 August and again from 6 September, with the usage meter running hot on light days. Root cause found, fixed and verified 9 September 2026. The fix did not stick: the opt-out was back in both the live and the committed settings on 10 September, and was removed again the same morning. Written by Claude Fable 5.1 from a background job on binky, with the within-day split and the per-model rows added 10 September by Claude Opus 5; the raw data and the eight-seat council review are listed at the end.

One setting and one URL check produced every 429

Two things had to be true at once for a classifier call to fail, on any CLI from 2.1.229 onwards. The settings file carried CLAUDE_CODE_ATTRIBUTION_HEADER=0, an opt-out that has sat there since 31 March. And the request had to leave through a base URL that is not api.anthropic.com, which is what the model-router gateway is. Either one alone is harmless. Together, Claude Code sends the classifier request without a block the server insists on, and the server answers a bare 429 in 0.3 seconds. Removing the opt-out ends it, and the gateway stays. Before 2.1.229 (released 12 August) the opt-out alone was enough, on every path, which is why auto mode also failed before the gateway existed; see the questions section below. Two of the roughly 270 errors in the window, both on 4 September with the gateway off, sit alongside 36 server-overload fallbacks that day and are ordinary overload, not this bug.

Auto mode makes a second, hidden request for every tool call

When the model proposes a tool call in auto mode, Claude Code does not run it straight away. It sends a separate request to a classifier, with the transcript attached, asking whether the action is safe. That request never appears in the session transcript file, so a scan of transcripts undercounts what the meter sees. The classifier runs on the session's model tier: Sonnet sessions classify on Sonnet, Fable sessions on Opus 5 with the 1M window.

flowchart TD
  A[Model proposes a tool call<br/>for example Bash] --> B{Allow or deny rule<br/>matches?}
  B -- yes --> R[Run or refuse locally<br/>no network call]
  B -- no --> C[Classifier request<br/>system prompt: security monitor<br/>body: transcript, about 188 KB<br/>max_tokens 64]
  C --> D{Server answer}
  D -- 200 verdict --> E[Run the tool<br/>or deny with a reason]
  D -- 429 --> F[Retry, up to 5 times]
  F --> G[Deny the tool<br/>Model re-plans at full context]

The re-plan is where the visible cost comes from. Every denied Bash sends the whole conversation back to the main model, at about 190k tokens on a typical session here, and the model tries a different route that gets denied again.

Claude Code drops the attribution block whenever both conditions hold

The attribution block is a short text line Claude Code puts into the system prompt of its own requests, naming the client and billing context. The opt-out variable suppresses it. Claude Code 2.1.229 added a repair for the classifier path, because the server rejects classifier requests without the block (Anthropic tracks this as issue 64585, the resolution of issue 60438). The repair has a guard: it only re-adds the block when the base URL is unset or its host is literally api.anthropic.com. The _CLAUDE_CODE_ASSUME_FIRST_PARTY_BASE_URL flag that the gateway sets is checked by a different function and does not reach this one.

flowchart TD
  A[Classifier request<br/>being assembled] --> B{Opt-out set?<br/>CLAUDE_CODE_ATTRIBUTION_HEADER=0}
  B -- no --> OK[Block included<br/>server answers 200]
  B -- yes --> C{Base URL host is<br/>api.anthropic.com<br/>or unset?}
  C -- yes, direct --> OK
  C -- no, gateway --> BAD[Block omitted<br/>server answers bare 429<br/>no retry-after, no headers]

Every captured request from the 8 September A/B lacked the block, on both arms, because both arms went through a loopback proxy URL. That is why that A/B showed no difference: it compared two failing paths and concluded, wrongly, that the router was innocent and Anthropic was throttling the account. The router was innocent, but for the reason above, not because the throttle was elsewhere.

Failures begin the hour the router came up

The router began listening at 09:07 UTC on 6 September and the wiring commit landed at 09:25, in the middle of the working day. Sessions on CLI 2.1.263 had been running since 03:00 UTC. Splitting that one day at 09:00 UTC therefore holds the CLI version, the session model, the machine and the account fixed, and varies only whether the request left through the gateway. Each cell below is failures over classifier-bound tool calls.

Sessions already running 2.1.263 made over a thousand classifier-bound calls that morning without a single failure, and began failing within the hour the router came up. That rules out the CLI version, the weekly model-scoped quota, the account and server-side capacity drift as the trigger, because none of them changed at 09:00 that day. The 2.1.261 row is listed for context rather than as a control: those sessions ran on the same machine-wide setting, so they vary the CLI version and nothing else.

The split also adds something the root cause above does not yet explain. The failures concentrate in Fable 5.1 sessions, whose classifier runs on Opus 5 with the 1M window. Opus 5 and Sonnet 5 sessions, whose classifier runs on Sonnet 5, stay at or near zero through the same gateway with the same opt-out set. So the missing attribution block appears to be refused on the Opus classifier lane and tolerated on the Sonnet lane, which is consistent with the model-dependent gating measured in issue 60438. Treat that as an observation, not a settled claim: a dropped block predicts uniform failure and says nothing about why the lane should matter. Five of the Opus 5 failures also name astra as their classifier rather than the Opus variant, which suggests the gateway sometimes mis-resolves which provider a classifier request belongs to.

Three limits. The denominator counts classifier-bound tool calls — Bash, PowerShell, Monitor, Agent, Task and SendMessage — which is an upper bound on classifier calls, because allow rules and cached verdicts skip the classifier. Three failures on tools outside that set, one Edit and two on an MCP browser tool, are excluded from every cell. And the gap between bound calls and real classifier calls moves with the workload mix, so a day-to-day rate series is not a trend; this within-day split is the comparison that survives. One further caution understates the second column rather than inflating it: a session fixes its base URL when it starts, so sessions launched before the rewire but still running after it sit in that column without the gateway.

The next section covers the same event day by day across three weeks, in local days, and the two are meant to be read together. Its 04:33 timestamp for the rewire is on the local clock and does not reconcile with the wiring commit's own 09:25 UTC, which is the boundary used here.

That is the "went away for two weeks, came back 14 hours ago" shape: the gateway was unwired on 18 August and rewired on 6 September.

Removing the setting fixed it and the gateway stays wired

The opt-out was removed from the live settings and committed as b2868c8a. The same headless auto-mode probe, one Bash command that creates and removes a file, ran before and after.

That removal did not hold, and the current state is the second one. On the morning of 10 September the opt-out was present again in both the live settings and the committed file. The likeliest reason is a session that started before the removal and wrote its own stale copy of the settings back, which is the same staleness the section below describes, acting on the file rather than on one process. It has now been removed from the live file and committed again as 963eaa2 on the worktree-classifier-failure-accounting branch. Landing the fix therefore needs three things: that commit merged, the daemon restarted, and every session started before the removal restarted with it.

The router could not have fixed this

The router never sees the block. Claude Code decides not to include it before the request leaves the process, so there is nothing for the router to forward or repair. The router could forge the line itself, but that would mean synthesising Anthropic's billing attribution on the client's behalf, which is the wrong side of the boundary and a plausible way to get an account flagged. The gap sits in Claude Code: its repair keys on the raw URL host instead of honouring the first-party flag it offers for exactly this gateway case. That is worth filing upstream. Until then, not setting the opt-out is the clean fix, and it costs nothing: the block is a billing attribution line, not data about the work.

What this does not fix

The 429s and the denial loops are gone. Three cost drivers are untouched, and were flagged by seven of eight council seats as the part the first diagnosis got backwards, since the heaviest spend days (2 to 4 September) had almost no 429s.

  • Every non-allowlisted tool call in auto mode still costs one classifier request on the session's model tier, about 47k mostly cached tokens each. Now that they succeed, they are billed where the 429s probably were not.
  • Long contexts. 29% of last week's requests carried 200k tokens or more, and 6% carried 400k or more. Compacting at task boundaries is the lever.
  • Nine parallel auto-mode sessions are nine classifier streams.

The levers the council agreed on: narrow permissions.allow rules for the read-only Bash patterns agents use most, deny rules and deterministic local PreToolUse hooks as classifier-free fast paths, a hook that stops a job after repeated identical denials, and compaction before 200k. Each allow rule's effect can be checked by counting classifier requests in the router log before rolling it out.

Sessions started before the fix still fail, and the daemon hands out stale ones

Settings env values are copied into the process environment when a Claude Code process starts, so every session launched before 22:21 PDT on 9 September still carries the opt-out and still 429s. The session that answered the review questions below is one: its process started at 17:30 PDT as a daemon pre-spawned spare, was claimed for a new job at 22:53, and showed CLAUDE_CODE_ATTRIBUTION_HEADER=0 in its environment. Transcripts logged 46 classifier refusals in that session's first hour, well after the fix, and re-authenticating and switching model did not clear them. The daemon keeps a pool of such spares, so a job started after the fix can still land on a pre-fix process. The fix is complete only after the daemon and every interactive session are restarted.

One thing does not fit and is left open. Refusals in that session were intermittent, while the 8 September capture was 15 failures out of 15. A handful of commands went through, including one git log, and half an hour later a plain git status was refused, so the difference is not which command was asked for. A stale opt-out predicts uniform failure, so either the server's 429 is not deterministic, or something besides the opt-out is throttling this account's classifier lane. Deciding between them needs the headless probe from the fix, run from a stale process and a fresh one, and that probe needs the shell access the refusals were blocking. Until it runs, treat the stale-process claim as the reason to restart, not as a closed case.

# which live claude processes still carry the opt-out
for p in $(pgrep -f claude); do ps -E -o command= -p "$p" | grep -q 'ATTRIBUTION_HEADER=0' && echo "$p stale"; done
# restart the daemon (this terminates background sessions), then reopen interactive sessions
claude daemon stop

Questions from the 9 September review, answered

Auto mode also failed before the gateway existed. Why? Because until 12 August the opt-out alone broke the classifier on every path. The v2.1.229 release notes (12 Aug 20:56) read: "Fixed auto mode failing on every tool call for users who disable the attribution header via CLAUDE_CODE_ATTRIBUTION_HEADER (direct Anthropic API connections)". That is issue 64585, opened 1 June by a reporter on the plain Anthropic API with no proxy, and issue 60438 from 19 May. The opt-out has been in the settings since 31 March, so from then until 12 August every auto-mode session failed, direct or not. The gateway was first wired on 13 August at 23:32, one day after the direct fix shipped, so the failures never visibly stopped: the cause narrowed from "opt-out anywhere" to "opt-out behind a gateway" overnight.

What is a re-plan? When the classifier denies a tool call, the tool does not run and the denial is returned to the model as the tool's result. The model then has to produce a new turn, which is a fresh request to the main model carrying the whole conversation, about 190k tokens on a typical session here. In the failing state each Bash cost five classifier attempts, one denial, one full-context re-plan, and then the model proposed another Bash and the cycle repeated.

Should this be filed upstream? Yes. The 2.1.229 repair re-adds the block only when the base URL host is literally api.anthropic.com, and ignores _CLAUDE_CODE_ASSUME_FIRST_PARTY_BASE_URL, the flag Claude Code itself offers for a first-party gateway. A draft issue is in the handover. The guard reading came from the 2.1.263 bundle in the earlier job; this session could not re-open the bundle because the classifier blocked the command, so the code-level claim rests on that read plus the release-note wording and the before/after probes. Confidence about 85%.

Is a gateway supported, and is the model-router against the terms? Gateways are a documented configuration. Anthropic's LLM gateway page says ANTHROPIC_BASE_URL "is the variable that points Claude Code at the gateway", and explicitly covers a subscription login through one: "a saved claude.ai login remains the active credential, so its usage limits and billing apply", provided the gateway forwards the OAuth capability beta. The same page says Anthropic "doesn't endorse, maintain, or audit third-party gateway products, and doesn't support routing Claude Code to non-Claude models through any gateway". Unsupported means no help when it breaks, not a stated breach. The Consumer Terms themselves were not read for this answer; the earlier note in docs/remote-control-and-foreign-models.md reached "probably not a breach on a plain reading". About 70% that the foreign-model routing is terms-clean; the Claude-through-gateway part is documented.

Why is billing involved at all? The block is Claude Code's billing-attribution line (x-anthropic-billing-header), which tells the server the request comes from Claude Code and in what context. Why the classifier lane insists on it is not stated anywhere by Anthropic. The shape of the failure suggests a server-side check that the request really is Claude Code's classifier: issue 60438 measured an instant 429 on Opus and Sonnet with a pass on Haiku, while ordinary messages to the same models succeeded, which is a gate, not a quota. Speculative, about 60%. Whether the failed attempts drew down the subscription meter is still open.

Are we sure it is fixed, and do sessions need restarting? The before/after probes on fresh processes succeeded through the router and direct. Yes to restarting: see the section above, where a pre-fix process was caught still failing at 23:00 on 9 September, after the fix. Answered again on 10 September, with a correction: the opt-out was back in both the live and the committed settings that morning, so the mechanism is verified but the removal was not durable. It has been removed and committed a second time as 963eaa2, and the fix lands only once that commit is merged and every pre-fix process, the daemon included, has been restarted.
